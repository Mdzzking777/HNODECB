日期：2026-03-12

主题：
AFM03 中 `in-place + GaussAdjoint(ReverseDiffVJP(true))` 的 reduced correctness 结果

1. 本次测试的目的
本次测试的目标不是看 runtime，而是回答一个更基础的问题：

- 如果把 Stage2 / Stage2light 改成
  - in-place RHS
  - `GaussAdjoint(autojacvec=ReverseDiffVJP(true))`
- 这条路线在 AFM03 上是否还能通过 reduced AD-vs-FD correctness 检查？

2. 本次实际改动
正式 Stage2 核心已改为：

- RHS: in-place
- sensealg: `GaussAdjoint(autojacvec=ReverseDiffVJP(true))`

也就是说，正式 `solve(...)` 现在不再走：

- out-of-place + `GaussAdjoint(ZygoteVJP())`

而是改成：

- in-place + `GaussAdjoint(ReverseDiffVJP(true))`

3. correctness 检查口径
这次没有使用旧的 standalone monkey-patch 逻辑。
检查脚本直接复用了正式 Stage2 的 loss 构造，只在 reduced `npts=8` 下做 AD-vs-FD。

检查对象包括：

- `p_mech_raw`
  - `ks_raw`
  - `cs_raw`

- sampled `p_net`
  - 共抽样 4 个 index

检查分支包括：

- `active`
- `state`
- `x2dot`

4. 结果
结论非常明确：

- 这条路线在 reduced AD-vs-FD 下不通过。

更具体地说：

4.1. `state` branch

- `p_mech` 的 AD 基本为 0
- `p_mech` 的 FD 明显非零
- sampled `p_net` 的 AD 也是 0
- sampled `p_net` 的 FD 明显非零

这意味着：

- `state loss -> solve trajectory -> parameters`

这条主敏感度链在当前路线下没有被正确传回来。

4.2. `active` branch

- `p_mech` 的 AD 仍然接近 0
- `p_mech` 的 FD 明显非零
- sampled `p_net` 的 AD 虽然不是严格 0
- 但与 FD 严重不一致，很多分量相对误差约为 100%

4.3. `x2dot` branch

- `p_mech` 的 AD 仍然接近 0
- `p_mech` 的 FD 明显非零
- sampled `p_net` 的 AD 有少量非零值
- 但与 FD 仍严重不一致

5. 当前最合理的解释
这次结果说明：

- 问题不只是 `p_mech` 某一维量级不准
- 也不只是 `p_net` 某些分量有噪声

而是：

- `GaussAdjoint(ReverseDiffVJP(true))`

在 AFM03 当前 formal Stage2 路线上，没有正确恢复参数对 ODE 轨迹的敏感度。

尤其 `state` branch 的现象最关键，因为 `state loss` 只依赖 `solve(...)` 给出的轨迹。
在这个分支上：

- AD 近零
- FD 非零

这强烈说明问题核心在：

- `solve(..., sensealg=GaussAdjoint(ReverseDiffVJP(true)))`

的 sensitivity path，而不是 loss 后处理本身。

6. 工程判断
因此，这条路线目前只能得出一个结论：

- `in-place + GaussAdjoint(ReverseDiffVJP(true))`

虽然前向能跑、sanity 能过，
但在 AFM03 上 reduced correctness 不通过，
因此不能作为可信的正式训练路线。

7. 本次记录的意义
这次结果有一个重要价值：

- 它排除了“只要从 ZygoteVJP() 退回 ReverseDiffVJP(true) 就能同时恢复可运行性和正确性”的想法。

也就是说：

- `ZygoteVJP()` 路线目前有 runtime / pathological 问题；
- 但 `ReverseDiffVJP(true)` 路线在 AFM03 上又重新暴露了 correctness 问题。

所以这不是一个简单的“换回 ReverseDiff 就解决”的问题。

8. `ReverseDiffVJP()`（默认 `compile=false`）的追加对照
在同一套 reduced gradcheck 口径下，又追加测试了：

- `GaussAdjoint(ReverseDiffVJP())`

也就是：

- `GaussAdjoint(ReverseDiffVJP(false))`

结果是：

1. 它没有修复 reduced AD-vs-FD correctness。
- sampled `p_net` 的表现几乎和 `ReverseDiffVJP(true)` 一样坏。
- 尤其 `state` branch 里，sampled `p_net` 的 AD 仍为 0，而 FD 明显非零。

2. `p_mech` 不再是严格接近 0，但仍然严重错误。
- 它只是从“几乎绝对 0”变成了“小的非零值”。
- 量级仍明显小于 FD，通常差 2 到 3 个数量级。
- 相对误差仍接近 100%。

3. backward 反而更慢。
- 在 reduced `npts=8` 的同口径检查里：
  - `ReverseDiffVJP(true)` 的 backward 大约是十几秒到几十秒量级；
  - `ReverseDiffVJP()` 的 backward 增加到了约 210 到 232 秒量级。

因此，这个对照说明：

- `true -> false`

并没有带来 correctness 改善，
反而增加了 runtime 成本。

10. 当前结论一句话版
`in-place + GaussAdjoint(ReverseDiffVJP(true))` 在 AFM03 上前向可运行，但 reduced AD-vs-FD 明显失败，尤其是 state-loss 对参数的主敏感度几乎丢失；而改成 `ReverseDiffVJP()` 也没有修复 correctness，反而更慢，因此这一整类 ReverseDiff-based Gauss route 目前都不能视为可信 formal route。
