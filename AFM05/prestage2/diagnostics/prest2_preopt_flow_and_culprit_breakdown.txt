AFM05 prest2 preopt flow and culprit breakdown
================================================

Purpose
-------
This note records what AFM05 prest2 does before formal epoch 1, and quantifies
which step causes the loss discontinuity between st1pl and prest2 entry.

The quantitative example below uses the typical candidate:

  candidate B01
  trial_id = 26055
  mech winner = 170
  ks0 = 2.069138081114790e-01
  cs0 = 1.405884348987116e-06

Source diagnostic:

  AFM05/prestage2/diagnostics/afm05_st1pl_vs_prest2_entry_loss_diagnostics.csv


Prest2 preopt flow before epoch 1
---------------------------------

1. Select st1pl candidate identity

   prest2 reads the st1pl candidate identity:

     trial_id, ks0, cs0, NN/KAN seed, KAN architecture, window metadata.

   Important: current prest2 does not directly load a full st1pl endpoint
   checkpoint or the original st1pl rollout trajectory.

2. Build the initial formal x3 normalizer

   The current formal prior is:

     state_mean[2]  = x1_mean
     state_scale[2] = 0.1 * x1_scale

   This is reconstructed inside stage2light/prest2 instead of being loaded as
   a complete st1pl endpoint state.

3. Build initial AGU support/grid

   x1 and x2 grid inputs come from the observed training window.
   x3 grid input is a neutral artificial support axis, not the actual st1pl
   x3_pred(t) density.

4. Reconstruct KAN and mechanistic modules

   KAN is reconstructed from the seed and architecture.
   The mechanistic module is initialized from ks0 and cs0.

5. Initialize gain

   The gain is initialized from the current training-window force reference.

6. First preopt rollout: prest2 attempts to reproduce the st1pl candidate

   This is the critical first rollout.  It happens before updating x3_mean,
   x3_scale, x3 support, or AGU from the preopt x3 trajectory.

   For B01:

     st1pl cached loss                    = 8.951094011082607e-10
     prest2 first pre-refit stage2 loss    = 1.819776579071086e-06

   This is already a ~2033x jump under the stage2 loss.

7. Compute x3 statistics from this prest2 preopt rollout

   From the prest2 preopt x3_pred(t):

     x3_mean  = mean(x3_pred)
     x3_scale = std(x3_pred)
     x3_norm_support = [
       min((x3_pred - x3_mean) / x3_scale),
       max((x3_pred - x3_mean) / x3_scale)
     ]

   For B01:

     x3_refit_mean        = 1.334905770599286e-09
     x3_refit_scale       = 1.159612148861203e-09
     x3_refit_support_min = -9.741769149343407e-01
     x3_refit_support_max =  2.757764233964993e+00

8. Update KAN normalizer and AGU

   prest2 replaces state_mean[2] and state_scale[2], constructs a new neutral
   x3 support/grid, and runs AGU/grid update.

9. Re-initialize gain

   Because the normalizer/grid changed, gain is initialized again.

   For B01:

     gain_before_refit = 8.362702010508403e-10
     gain_after_refit  = 3.842536471806096e-10

10. Second preopt rollout after x3 refit

    This produces loss_after_x3_refit.

    For B01:

      loss_before_x3_refit = 1.819776579071086e-06
      loss_after_x3_refit  = 1.668283255884675e-06

    Therefore, x3 refit slightly improves the preopt loss.  It is not the
    source of the st1pl-to-prest2 discontinuity.

11. Initialize epoch-0 monitoring baseline

    The post-refit rollout becomes the baseline for later monitoring, including
    x3 drift.

12. Enter formal optimization

    Adam/LBFGS epochs begin only after the above preopt sequence.


Four diagnostic evaluations
---------------------------

For B01:

  eval1 = st1pl rollout + st1pl loss
        = 8.951094011082607e-10

  eval2 = st1pl saved x1/x2/x2dot error components converted to stage2
          RMS normalization
        = 7.192083782987207e-09

  eval3 = prest2 first pre-refit rollout + st1pl-style loss
        = 2.240399622267243e-07

  eval4 = prest2 first pre-refit rollout + stage2 loss
        = 1.819776579071086e-06

  post-refit stage2 loss
        = 1.668283255884675e-06


Culprit breakdown
-----------------

The target discontinuity is:

  st1pl cached loss -> prest2 first pre-refit stage2 loss
  8.951094011082607e-10 -> 1.819776579071086e-06

Total jump:

  ratio  = 2033.021x
  log10  = 3.308 dex

Because this is a multi-order-of-magnitude jump, the contribution is measured
on a log scale.

Step A: prest2 first rollout fails to reproduce st1pl endpoint

  st1pl loss -> prest2 pre-refit rollout under st1pl-style loss

  8.951094011082607e-10 -> 2.240399622267243e-07

  ratio = 250.293x
  log10 = 2.398 dex

  culprit share = 72.5%

  Interpretation:
  this is the main discontinuity.  Even before applying the stage2 RMS loss
  definition, the prest2 pre-refit trajectory is already much worse than the
  st1pl trajectory.  Therefore the primary issue is not the loss formula, but
  the fact that prest2 reconstructs a new entry rollout rather than loading a
  fully reproducible st1pl endpoint.

Step B: stage2/prest2 RMS loss normalization further amplifies the mismatch

  prest2 pre-refit rollout under st1pl-style loss -> prest2 pre-refit rollout
  under stage2 loss

  2.240399622267243e-07 -> 1.819776579071086e-06

  ratio = 8.123x
  log10 = 0.910 dex

  culprit share = 27.5%

  Interpretation:
  loss normalization is a real amplifier, but not the main cause.  It explains
  only the final ~8x on top of an already-broken pre-refit rollout.

Step C: x3_mean/x3_scale/support/AGU refit

  prest2 first pre-refit stage2 loss -> post-refit stage2 loss

  1.819776579071086e-06 -> 1.668283255884675e-06

  ratio = 0.917x
  log10 = -0.038 dex
  linear reduction = 8.32%

  culprit share = negative / not guilty

  Interpretation:
  x3 refit does not cause the st1pl-to-prest2 jump in this case.  It slightly
  reduces the preopt loss after the first prest2 rollout has already diverged
  from st1pl.


Short conclusion
----------------

The st1pl-to-prest2 discontinuity is dominated by the first prest2 pre-refit
rollout, i.e. by prest2 failing to reproduce the original st1pl endpoint.

Loss-scale differences are secondary amplifiers.

x3_mean/x3_scale/support/AGU refit is not the culprit for the initial jump; in
the B01 diagnostic it slightly lowers the loss.

Practical implication:

  If prest2 is intended to be a continuation of st1pl, it should not silently
  accept a reconstructed preopt rollout whose loss no longer matches st1pl.
  The cleaner design is:

    1. st1pl saves a reproducible endpoint state or full entry snapshot;
    2. prest2 loads it;
    3. prest2 verifies loss/observable errors match st1pl;
    4. only then prest2 performs x3 normalizer/support/AGU refit and enters
       epoch 1.


Correction after July 2026 prest2 entry refactor
------------------------------------------------

The original culprit statement above was correct for the old prest2 flow, but
the concrete cause must be stated more sharply:

  The old prest2 first pre-refit rollout was not using the same formal x3
  prior center as st1pl.

In st1pl, the formal x3 normalizer was:

  state_mean[2]  = x3(t0)
  state_scale[2] = 0.1 * x1_scale

In the old stage2light/prest2 data entry, the formal x3 normalizer was:

  state_mean[2]  = x1_mean
  state_scale[2] = 0.1 * x1_scale

For the current AFM05 window this caused an x3 center shift of about
6.41e-9 m, approximately 1.48 normalized x3 units.  This is enough to move the
third KAN input through a substantially different spline/grid coordinate, so
the pre-refit prest2 entry model could not reproduce the st1pl rollout even
before any x3 refit was performed.

Therefore, the historical old-prest2 first-rollout discontinuity should be
attributed primarily to this entry normalizer mismatch:

  st1pl used x3(t0), while old prest2 used x1_mean.

This issue is obsolete for the current prest2 design:

  The updated prest2/st2l entry path no longer performs the extra preopt
  reproduce rollout whose purpose was to re-create the st1pl endpoint.  Instead,
  when st1pl metadata are available, prest2/st2l directly inherit the
  st1pl-provided x3 entry metadata (rs_x3_pred_mean, rs_x3_pred_scale, and
  rs_x3_norm_support).  Thus the old "first pre-refit rollout" diagnostic is a
  historical explanation for old runs, not a required step in the current
  prest2 pipeline.

The stage2light data prior was nevertheless corrected to match st1pl:

  state_mean[2] = x3(t0)

This keeps fallback/random/stage2-only entry behavior consistent with st1pl,
but this prior is not the main prest2 path when valid st1pl x3 entry metadata
are present.
